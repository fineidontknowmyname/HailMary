Section 01

The Document Paradigm

MongoDB doesn't store JSON; it stores BSON (Binary JSON). This fundamental difference powers its performance.

📦
BSON Storage
BSON is optimized for data locality and read speed. It allows MongoDB to traverse documents quickly and supports native data types like Dates, ObjectIDs, and decimals that pure JSON lacks.
⚡
Data Locality
Because related data is stored together in a single document, a single read operation retrieves everything. You avoid the costly JOINs required by relational databases.
🛡️
Schema Validation
MongoDB is "flexible," but not necessarily "schemaless." You can enforce JSON Schema validation at the collection level to ensure documents have required fields and proper data types.
Section 02

CRUD Optimization

Write code that respects the network. Optimization starts at the query level.

1
Atomic Single-Document Operations
In MongoDB, any operation on a single document is atomic. Whether you're updating one field or fifty, the document will always be in a consistent state. Use operators like $inc or $push instead of reading, modifying, and saving back.
2
Use Projections
Never use find() to fetch a 10MB document if you only need the user's name. Use projections to limit the fields returned. This reduces memory usage on the database, reduces network payload, and speeds up deserialization in your application.
3
High-Throughput bulkWrite
When inserting or updating hundreds of documents, use bulkWrite(). It groups operations together, drastically reducing the number of network round-trips compared to looping through individual insertOne() calls.
Section 03

Schema Design: Embed vs. Reference

The most critical decision in NoSQL architecture. Make the wrong choice and you will hit hard system limits.

💡
Embedding is the Default
For "one-to-few" relationships (like a user's shipping addresses or profile settings), embed the data as a sub-document or array. This maximizes data locality and read performance.
⚠️
The 16MB Document Limit
MongoDB documents have a strict 16MB size limit. If a relationship involves unboundedly growing data (like thousands of reviews for a popular product, or logs for a system), you must reference the data in a separate collection. If you embed it, the document will eventually crash your application when it breaches 16MB.
Section 04

The ESR Indexing Rule

The golden rule for compound indexes: Equality, Sort, Range. Following this rule eliminates expensive in-memory sorts.

1️⃣
E - Equality
First, index fields that your query tests for exact matches (e.g., { status: "active" }). This narrows down the result set as quickly as possible.
2️⃣
S - Sort
Second, index the fields you use to order the results (e.g., .sort({ createdAt: -1 })). If the index matches the sort, MongoDB avoids a blocking, memory-intensive sorting operation.
3️⃣
R - Range
Finally, index fields used for range queries (like $gt, $lt, or $in). Once a range is evaluated, the index can no longer be used for sorting, which is why it must come last.
Section 05

The Aggregation Framework

A powerful pipeline for data transformation, but one that can easily overwhelm your database if used carelessly.

1
Filter Early with $match
Always place your $match stages as early in the pipeline as possible. If placed first, $match can use indexes. This drastically reduces the number of documents passed to expensive subsequent stages like $group or $lookup.
2
The 100MB RAM Limit
By default, a single aggregation pipeline stage is only allowed to consume 100MB of RAM. If your $group or $sort operation exceeds this, the query will fail.
3
The allowDiskUse Safety Valve
If you anticipate a stage will breach the 100MB limit, you can pass { allowDiskUse: true } to the aggregation options. This allows MongoDB to write temporary files to disk. It's slower, but ensures the query succeeds.
Section 06

Monitoring & Performance

You can't optimize what you don't measure. Keep a close eye on the WiredTiger storage engine.

⚙️
The WiredTiger Cache
WiredTiger is the engine room of MongoDB. It utilizes an internal cache (typically 50% of available RAM minus 1GB). Watch your metrics for Application Thread Eviction — this indicates your cache is full and application threads are being paused to evict old data to disk. It's a prime sign of memory pressure.
🔢
The Counting Trap
Do not use countDocuments() on large collections just to get a total row count! It performs a full index scan to guarantee accuracy, which is incredibly slow. If you just need a fast, approximate total, use estimatedDocumentCount(), which reads metadata instantly.
