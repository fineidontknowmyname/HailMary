Section 01

Core Concepts — The Mental Model

Before touching any command, lock in these four concepts. Everything else in Docker builds on them.

😤
Developer's Law — The Problem Docker Solves
"It works on my machine." Your app runs perfectly locally but crashes on your teammate's laptop or on the production server. Different OS, different dependency versions, different environment variables. Docker packages everything into a single portable unit so this never happens.
🖼️ Image — The Recipe
A read-only template containing your code, runtime (e.g. Node.js), dependencies, OS tools, and environment settings. Like an installation CD — it defines everything needed to run your app, but it isn't running yet. One image can create many containers.
📦 Container — The Running Meal
A live, isolated instance created from an image. Like a sandboxed mini-computer running on your machine. It has its own filesystem, network, and processes — but shares the host OS kernel. Lightweight and disposable by design.
🗂️
Dockerfile
A plain text file with step-by-step instructions for building an image. Think of it as the recipe you write. Docker reads it top to bottom, executing each instruction as a layer.
🎼
Docker Compose
A YAML config file that defines and runs multi-container applications. Instead of typing 5 long docker run commands, you write one file and run docker compose up.
💾
Docker Volume
Persistent storage that lives outside the container. Containers are ephemeral — when they stop, their internal data is gone. Volumes save data to the host machine so it survives restarts and deletions.
🌐
Docker Network
A virtual network that lets containers talk to each other by name. Without a shared network, your backend container can't reach your database container — even on the same machine.
🏪
Docker Hub
The public registry for Docker images. Like npm for Node or PyPI for Python — but for container images. Pull official images (Postgres, MongoDB, Node) or push your own custom builds here.
⚡
Layer Caching
Docker caches each instruction in a Dockerfile as a "layer." If a layer hasn't changed, Docker reuses the cache and skips rebuilding it — making subsequent builds dramatically faster.
Section 02

Install & Setup

Get Docker running on your machine in under 5 minutes. One download gives you everything.

1
Download Docker Desktop
Go to docker.com and download Docker Desktop for your OS (Mac, Windows, or Linux). Docker Desktop bundles the Docker Engine, CLI, Docker Compose, and a GUI dashboard — all in one installer.
2
Verify Installation
Open your terminal and confirm everything installed correctly.
Terminal
docker --version
# Docker version 26.x.x

docker compose version
# Docker Compose version v2.x.x

docker run hello-world
# Pulls a test image and prints "Hello from Docker!"
3
Install the IDE Extension
If you use VS Code, install the official Docker extension by Microsoft. It adds syntax highlighting for Dockerfiles and Compose files, lets you manage containers/images from the sidebar, and shows real-time logs without touching the terminal.
4
Pull Your First Image from Docker Hub
Try pulling an official database image. No installation wizard, no version conflicts — Docker downloads the exact image and it's ready to run.
Terminal
# Pull the official Postgres image
docker pull postgres

# List all downloaded images
docker images
🐳
docker init — The Fast Lane
Run docker init inside any existing project folder. Docker will inspect your code, ask a few questions, and automatically generate a Dockerfile, .dockerignore, and compose.yaml — perfectly configured for your stack. Skip manual setup entirely.
Section 03

Writing a Dockerfile

A Dockerfile is how you tell Docker exactly how to package your application. Each line is an instruction that creates a new layer in the image.

Dockerfile Instructions Reference

InstructionWhat It DoesExample
FROMSets the base image to build on top of. Always the first line.FROM node:20-alpine
WORKDIRSets the working directory inside the container for all following commands.WORKDIR /app
COPYCopies files from your host machine into the container.COPY . .
RUNExecutes a shell command during the build phase (installing packages, etc).RUN npm install
ENVSets environment variables inside the container.ENV NODE_ENV=production
EXPOSEDocuments which port the container listens on (informational only).EXPOSE 3000
CMDThe default command to run when the container starts. Only one per Dockerfile.CMD ["node", "server.js"]

Complete Example — Node.js App

Dockerfile
# 1. Use official Node.js base image (alpine = lightweight)
FROM node:20-alpine

# 2. Set working directory inside container
WORKDIR /app

# 3. LAYER CACHE TRICK: Copy package files FIRST
COPY package.json package-lock.json ./

# 4. Install dependencies (cached unless package.json changes)
RUN npm install

# 5. NOW copy the rest of the source code
COPY . .

# 6. Set environment variable
ENV NODE_ENV=production

# 7. Document the port this app runs on
EXPOSE 3000

# 8. Command to start the server when container runs
CMD ["node", "server.js"]
⚡
The Layer Caching Trick — Always Do This
Copy package.json and run npm install before copying your source code. Why? If only your source code changes (not your dependencies), Docker reuses the cached npm install layer and skips reinstalling everything. This turns a 90-second build into a 3-second build.

The .dockerignore File

.dockerignore
# Exclude these from being copied into the image
node_modules
.env
.git
*.log
dist
README.md
💡
Python App? Same Structure
For a Python/Flask app: use FROM python:3.11-slim, copy requirements.txt first, run pip install -r requirements.txt, then copy the rest of your code. The layer caching principle is identical across all languages.
Section 04

Essential CLI Commands

The commands you'll use daily. Memorize these and you can manage 90% of Docker workflows from the terminal.

Building & Running

CommandWhat It Does
docker build -t myapp .Build an image from the Dockerfile in the current directory, tag it as "myapp"
docker run myappStart a container from the "myapp" image
docker run -d myappRun in detached mode (background) — terminal stays free
docker run -p 3000:3000 myappRun with port forwarding: host port 3000 → container port 3000
docker run -e PORT=3000 myappPass an environment variable into the container

Managing Containers & Images

CommandWhat It Does

docker ps -aList all containers including stopped ones
docker imagesList all downloaded/built images
docker stop <id>Gracefully stop a running container
docker rm <id>Delete a stopped container
docker rmi <image>Delete an image
docker system pruneClean up all stopped containers, unused networks, and dangling images

Debugging

CommandWhat It Does

docker logs -f <id>Follow logs in real-time (like tail -f)

🖥️

Everything above can also be done in Docker Desktop's UI. Click any container to see its logs, environment variables, port mappings, volume mounts, and resource usage — great for debugging without memorizing every CLI flag.
Section 05

Port Mapping & Networking

Containers are isolated — they can't automatically talk to your browser or to each other. You have to explicitly connect them.

1
Port Mapping — Host to Container
A container's internal port is fixed (e.g., Postgres always uses 5432 internally). You map it to a free port on your host machine using the -p host:container flag. This is how your browser reaches your containerized app.
Port Mapping Examples
# Map host:3000 → container:3000
docker run -p 3000:3000 myapp

# Run two Postgres instances on different host ports
docker run -p 5432:5432 postgres  # Instance 1
docker run -p 5433:5432 postgres  # Instance 2 (different HOST port)
2
Container-to-Container Networking
For two containers to talk to each other (e.g., a backend and a MongoDB database), they must be on the same Docker network. Create a network and attach both containers to it — they can then reference each other by container name as the hostname.
Manual Network Setup
# Create a shared network
docker network create my-network

# Run MongoDB on the network
docker run -d \
  --name mongodb \
  --net my-network \
  -e MONGO_INITDB_ROOT_USERNAME=admin \
  -e MONGO_INITDB_ROOT_PASSWORD=secret \
  mongo

# Run Mongo Express (UI) on the same network
docker run -d \
  --name mongo-express \
  --net my-network \
  -p 8081:8081 \
  -e ME_CONFIG_MONGODB_SERVER=mongodb \
  mongo-express
📡
Use Docker Compose instead
Writing long docker run commands with --net flags is error-prone and hard to repeat. Docker Compose handles networking automatically — all services in the same Compose file share a network by default and can reference each other by their service name.
Section 06

Volumes — Persistent Data

Containers are ephemeral. Every time a container stops, its internal state is wiped. Volumes are how you save data permanently.

⚠️
Without Volumes — Data Dies With the Container
Start a database container, insert some records, then stop the container. Start it again — everything is gone. For databases, user uploads, or any state that needs to survive, you must attach a Volume.
Attaching a Volume via CLI
# -v host_path:container_path
# Maps /my/local/data on host → /data/db inside container
docker run -d \
  -v /my/local/data:/data/db \
  -p 27017:27017 \
  mongo
Named Volume (Recommended)
# Docker manages the storage location for you
docker run -d \
  -v mongo-data:/data/db \
  mongo

# List all volumes
docker volume ls
Section 07

Docker Compose — Multi-Container Apps

Stop running 5 separate terminal commands. Define your entire application stack in one YAML file and start everything with a single command.

💡
One Container Per Service
Never cram your frontend, backend, and database into a single container. Each service should run in its own container. Docker Compose is what orchestrates them — connecting them together, managing startup order, and sharing volumes and networks automatically.

Full Example — Backend + MongoDB + Mongo Express

compose.yaml
version: '3.8'

services:

  # ─── Your Node.js Backend ───────────────────
  backend:
    build: .               # Build from Dockerfile in this folder
    ports:
      - "3000:3000"
    environment:
      - MONGO_URL=mongodb://admin:secret@mongodb:27017
    depends_on:
      - mongodb             # Start MongoDB first
    volumes:
      - ./src:/app/src      # Live code sync for dev

  # ─── MongoDB Database ───────────────────────
  mongodb:
    image: mongo
    ports:
      - "27017:27017"
    environment:
      - MONGO_INITDB_ROOT_USERNAME=admin
      - MONGO_INITDB_ROOT_PASSWORD=secret
    volumes:
      - mongo-data:/data/db  # Persist database data

  # ─── Mongo Express Web UI ───────────────────
  mongo-express:
    image: mongo-express
    ports:
      - "8081:8081"
    environment:
      - ME_CONFIG_MONGODB_SERVER=mongodb
      - ME_CONFIG_MONGODB_ADMINUSERNAME=admin
      - ME_CONFIG_MONGODB_ADMINPASSWORD=secret
    depends_on:
      - mongodb

# ─── Named Volumes Declaration ──────────────
volumes:
  mongo-data:

Docker Compose Commands

CommandWhat It Does
docker compose upStart all services defined in compose.yaml
docker compose up -dStart in detached (background) mode
docker compose up --buildRebuild images before starting (use after code changes)
docker compose downStop and remove all containers (data in volumes is kept)
docker compose down -vStop containers AND delete volumes (wipes all data)
docker compose logs -fFollow live logs from all services
docker compose psList all services and their status
Section 08

Docker Hub — Share Your Images

Push your custom-built images to Docker Hub so they can be pulled on any server or shared with your team — just like pushing code to GitHub.

1
Login from the CLI
Create a free account at hub.docker.com, then authenticate from your terminal.
Terminal
docker login
# Enter your Docker Hub username and password
2
Tag Your Image
Docker Hub images follow the format username/imagename:tag. Tag your local image to match this format before pushing.
Terminal
# Tag format: username/repo:version
docker tag myapp yourname/myapp:1.0
docker tag myapp yourname/myapp:latest
3
Push to Docker Hub
Upload your image to the registry. Anyone on any machine can now pull and run it.
Terminal
docker push yourname/myapp:latest

# On any other machine, pull and run it:
docker run -p 3000:3000 yourname/myapp:latest
🔍
Understanding Tags & Versions
On Docker Hub, tags are version identifiers. postgres:16, postgres:16-alpine, postgres:latest are all different tags of the same image. Always pin to a specific version in production — using :latest can break things when a new version is released.
Section 09

Best Practices & Key Takeaways

The most important lessons distilled from both videos. Keep these in mind on every project.

📋
Layer Cache Order Matters
Always copy dependency files (package.json, requirements.txt) and install them before copying source code. Unchanged dependencies = cached layer = fast builds.
💀
Containers Are Disposable
Never treat a container as permanent. They can be stopped, deleted, and recreated at any time. Any important data must live in a Volume — never inside a container's filesystem.
🔀
One Service Per Container
Don't put your frontend, backend, and database in a single container. Run each service in its own container. Docker Compose is specifically designed to wire them all together.
🔒
Never Hardcode Secrets
Don't put passwords, API keys, or tokens directly in your Dockerfile or compose.yaml. Use a .env file, add it to .gitignore and .dockerignore, and reference it as env_file in Compose.
🏔️
Use Alpine Base Images
Choose node:20-alpine or python:3.11-slim over full OS images. Alpine images are ~5MB vs ~200MB for standard images — much faster to pull and smaller attack surface for security.
🏗️
DevOps Doesn't Mean Knowing the Code
To containerize an app, you only need to know: the base environment (e.g. Python 3.11), how to install dependencies, the port it runs on, and the start command. You don't need to understand the business logic.
☁️
Docker Build Cloud — For Slow Builds
If your images take a long time to build (complex ML projects, monorepos, etc.), Docker Build Cloud offloads the build process to the cloud and shares the build cache with your entire team. Every developer gets fast first-time builds — no more waiting 10 minutes locally.
📖
Always Read the Official Docs
Docker's documentation at docs.docker.com is excellent. Every official image on Docker Hub (Postgres, MongoDB, Redis, etc.) has a detailed README explaining all available environment variables, volume mount paths, and run commands. Read it before fighting with a container that won't start.
