Section 01

Git vs. GitHub — Know the Difference

The most common beginner confusion. Git and GitHub are two completely different things that work together.

🛠️
Git — The Local Tool
A free, distributed version control system installed on your computer. It tracks every change you make to files over time, lets you go back to any previous version, and lets multiple people work on the same codebase. Like a "save history" on steroids — it works entirely offline.
☁️
GitHub — The Cloud Platform
A website and hosting service for Git repositories. Think of Git as the coffee, GitHub as the coffee shop. GitHub lets you back up your Git history online, share code with others, collaborate via Pull Requests, and deploy projects. GitLab and Bitbucket are alternatives.
💡
Distributed vs. Centralized VCS
Older systems like Subversion (SVN) and TFS were centralized — one server held all history and if it went down, everyone was stuck. Git is distributed — every developer has a full copy of the entire history on their machine. No single point of failure, and you can work fully offline.
Section 02

Setup & Configuration

Install Git and configure your identity once globally. Git uses this information to sign every commit you make.

1
Install Git
Download from git-scm.com. On Mac you can also install via Homebrew: brew install git. Verify the install with git --version.
2
Configure Your Identity
Run these once — Git attaches this name and email to every commit you make forever.
Terminal — One-time Global Config
# Set your name and email globally
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

# Set VS Code as the default editor
git config --global core.editor "code --wait"

# Handle line endings (Windows users: input | Mac/Linux: auto)
git config --global core.autocrlf input

# View all your settings
git config --list
3
Ways to Use Git
Three options — all valid. Most developers primarily use the command line. Command Line (terminal / Git Bash) — most powerful and universal. IDE Integration (VS Code has built-in Git) — convenient for quick operations while coding. GUI Clients (GitKraken, SourceTree) — visual interface, great for visualizing branches.
Section 03

The 3-Stage Workflow

Everything in Git revolves around three areas. Understanding this mental model unlocks every other command.

Stage 1
Working Directory
Where you write and edit files normally
──
git add
Stage 2
Staging Area
Propose a snapshot of selected changes
──
git commit
Stage 3
Repository (.git)
Permanently recorded snapshot in history
──
git push
Remote
GitHub
Backed up online, shareable with team
📁
Working Directory
Your normal project folder where you create, edit, and delete files. Git watches this folder and knows when things change — but doesn't record anything automatically. Files here are either tracked (Git knows about them) or untracked (brand new, Git hasn't seen them yet).
📋
Staging Area (Index)
A "draft" area where you prepare exactly what will go into the next commit. You pick and choose which changes to include — you don't have to commit everything at once. The staging area holds complete snapshots of files, not just diffs. If you modify a file after staging it, you must stage it again.
🗄️
Repository (.git folder)
The hidden .git folder in your project root. This is Git's database — every commit, branch, tag, and object in your project's entire history lives here. Never manually edit files inside it. HEAD is a pointer to the currently checked-out commit or branch.
🔑
Initialize a New Repository
Run git init inside any project folder to turn it into a Git repository. This creates the hidden .git directory. Alternatively, run git clone <url> to download an existing repository from GitHub — this automatically sets up tracking for the remote.
Section 04

Staging & Committing

The commands you'll type dozens of times every day. The daily loop: check status → stage changes → commit with a message.

1
Check What's Changed
Always start here. See which files are modified, staged, or untracked before doing anything else.
Status Commands
git status          # Full status with explanations
git status -s       # Short format: M=modified, ??=untracked, A=staged
2
Stage Your Changes
Add files to the staging area. You have a few options depending on what you want to include.
Staging Options
git add file.js        # Stage a single file
git add .              # Stage all changes in current directory
git add -A            # Stage ALL changes in entire project (inc. deletions)
git add *              # Stage all EXCEPT deleted files
git add src/           # Stage all changes in a folder
3
Commit the Snapshot
Record the staged changes permanently in history. Write commits in present tense ("Add login feature" not "Added login feature"). Keep commits small and logically focused.
Commit Commands
git commit -m "Add user authentication"

# Skip staging — commit all TRACKED modified files directly
git commit -a -m "Fix navbar alignment"

# Fix the most recent commit message (before pushing)
git commit --amend -m "Better message"
✍️
Commit Best Practices
Commit frequently and keep each commit focused on one logical change. Never dump 2 days of work into a single giant commit. Good commit messages make debugging and code review dramatically faster. Think: "What would I want to read in 6 months when investigating a bug?"
Section 05

Viewing History & Diffs

Inspect what changed, when, and by whom. Always review changes before committing them.

Viewing Commit History

CommandWhat It Shows
git logFull history with author, date, and full commit message
git log --onelineCompact view — one line per commit with short SHA and message
git log --oneline --all --graphVisual branch graph in the terminal
git show <commit-sha>Full details of a specific past commit — what changed, what files
git diff <sha1> <sha2>Compare two specific commits and see exactly what changed

Reviewing Changes Before Committing

Diff Commands
# Show unstaged changes (working dir vs staging area)
git diff

# Show staged changes (staging area vs last commit)
git diff --staged

# Open VS Code as a visual diff tool instead
git difftool
git difftool --staged
🔎
Set VS Code as Your Visual Diff Tool
Run these once: git config --global diff.tool vscode and git config --global difftool.vscode.cmd "code --wait --diff $LOCAL $REMOTE". Now git difftool opens VS Code's side-by-side diff view instead of the terminal output.
Section 06

Undoing Changes

Made a mistake? Git has multiple ways to undo — pick the right tool for the situation. Some are safe, some are destructive.

↩️
git restore — Everyday Undos
The modern, safe tool for undoing local changes. Use it to unstage files, discard edits, or pull a file from a past commit. It only affects your working directory and staging area — it never touches commit history.
🔃
git revert — Safe History Undo
Creates a brand new commit that reverses the changes of a specific past commit. History is preserved. Safe to use on shared/public branches because it doesn't rewrite history — it just adds a new "undo" commit on top.
⏪
git reset — Rewrite History
Rolls back your commit history to a specific point. Dangerous on shared branches — it rewrites history, which breaks other people's copies. Only use on your own private local branches before pushing.
Undo Commands — Cheat Sheet
── git restore (no history changes) ──────────────────
git restore --staged file.js     # Unstage a file (keep edits in working dir)
git restore file.js              # Discard local edits (restore to last commit)
git restore --source=HEAD~1 file.js # Restore file from 1 commit ago
git clean -fd                  # Remove ALL untracked files and folders

── git revert (safe, creates new commit) ─────────────
git revert a1b2c3d              # Undo commit a1b2c3d by creating a reversal commit

── git reset (dangerous, rewrites history) ───────────
git reset --soft HEAD~1          # Undo last commit, keep changes STAGED
git reset HEAD~1                  # Undo last commit, keep changes in working dir
git reset --hard HEAD~1          # Undo last commit, DISCARD all changes (destructive)
☠️
Never git reset on a shared branch
If you've already pushed commits to a branch your team is working on, git reset will rewrite history that others have already pulled. This causes everyone's history to diverge and creates a nightmare to fix. Use git revert instead — it's always safe on shared branches.
Section 07

Managing Files & .gitignore

Rename, delete, and tell Git which files to completely ignore — like build artifacts, credentials, and node_modules.

File Management Commands
# Delete a file AND stage the deletion in one command
git rm file.js

# Force delete a file that has staged changes
git rm -f file.js

# CRITICAL: Stop tracking a file without deleting it from disk
# (Use this when you accidentally committed node_modules or .env)
git rm --cached file.js

# Rename a file AND stage the rename in one command
git mv old-name.js new-name.js

The .gitignore File

.gitignore
# ── Node.js ───────────────────────
node_modules/
dist/
build/

# ── Secrets & Environment ─────────
.env
.env.local
*.pem

# ── OS & Editor junk ──────────────
.DS_Store
Thumbs.db
.vscode/settings.json

# ── Logs ──────────────────────────
*.log
logs/
⚠️
.gitignore Only Works for Untracked Files
If you accidentally committed node_modules or .env before adding them to .gitignore, adding them to .gitignore now won't stop Git from tracking them. You must first run git rm --cached node_modules -r to remove them from Git's index (tracking), then commit that change. The files stay on your hard drive — Git just stops watching them.
📂
Pre-made .gitignore Templates
Visit github.com/github/gitignore for official, language-specific .gitignore templates — Node.js, Python, Java, Unity, Android, and more. Copy and paste the relevant one into your project. Or when creating a new repo on GitHub, it can auto-generate one for you.
Section 08

Branching & Merging

Branches let you work on new features or bug fixes in total isolation from the main codebase. The single most important concept for team collaboration.

main    ──●──●──●─────────────────●── (merge)
                    \                  /
feature              ●──●──●──●──●──
1
Create & Switch Branches
Create a new branch for every feature or bug fix. Never commit experimental code directly to main.
Branch Commands
git branch                       # List all local branches
git branch feature/login          # Create a new branch
git checkout feature/login        # Switch to that branch

# Shortcut: create AND switch in one command
git checkout -b feature/login     # Modern equivalent:
git switch -c feature/login
2
Merge a Branch
When your feature is done, merge it back into main. Switch to the branch you're merging into first.
Merge Workflow
# 1. Switch to the target branch
git checkout main

# 2. Merge the feature branch into main
git merge feature/login

# 3. Delete the branch after merging (clean up)
git branch -d feature/login
3
Resolve Merge Conflicts
A conflict happens when two branches edit the same lines of the same file. Git pauses the merge and marks the conflicting sections. You manually choose which version to keep (or combine both), then commit the resolution.
What a Conflict Looks Like in Your File
<<<<<<< HEAD (your current branch)
const greeting = "Hello World";
=======
const greeting = "Hi there!";
>>>>>>> feature/login (incoming branch)

# Step 1: Edit the file — delete the markers, keep what you want
# Step 2: Stage the resolved file
git add file.js
# Step 3: Complete the merge
git commit -m "Merge feature/login — resolve greeting conflict"
4
Check Out a Past Commit
You can "time-travel" to any past state by checking out an old commit SHA. Your files revert to exactly that point in history. This puts you in "detached HEAD" state — don't make commits here. Use it for inspection only, then return with git checkout main.
Time-travel
git checkout a1b2c3d   # Go to this exact past state
git checkout main       # Return to the present
Section 09

Remote Repositories & GitHub

Connect your local Git history to the cloud. Push your code to GitHub to back it up and share it with your team.

1
Connect to a Remote
Create a new repository on GitHub, then link your local repo to it. origin is the conventional nickname for your primary remote.
Connecting Remote
# Link local repo to GitHub remote
git remote add origin https://github.com/you/repo.git

# Or clone an existing repo from GitHub
git clone https://github.com/you/repo.git

# List configured remotes
git remote -v
2
Push — Upload to GitHub
Send your local commits to GitHub. The first time you push a new branch, use -u to set the upstream — after that, plain git push is enough.
Push Commands
# First push — set upstream tracking
git push -u origin main

# All subsequent pushes on this branch
git push

# Push a feature branch
git push origin feature/login
3
Pull & Fetch — Download from GitHub
git pull is actually two commands in one: git fetch (downloads remote changes) + git merge (combines them into your local branch). Use fetch when you want to see what changed on the remote before merging.
Fetch vs Pull
# Download + merge (most common daily command)
git pull

# Download ONLY — don't merge yet (safe preview)
git fetch
# Then merge when ready:
git merge origin/main
Section 10

Stash, Rebase & Pull Requests

The tools that separate good Git users from great ones. Handle interruptions, clean up messy history, and collaborate via Pull Requests.

📦
git stash — Emergency Pause
You're halfway through a feature when your manager asks you to urgently fix a bug on main. You're not ready to commit. git stash saves your half-finished work to a temporary shelf, cleans your working directory, and lets you switch branches. Come back and restore it later.
📐
git rebase — Clean History
Instead of a merge commit that creates a branching history, rebase "replays" your commits on top of another branch — producing a clean, linear commit history. Easier to read in git log. Warning: Never rebase commits that have already been pushed to a shared remote branch.
🔀
Pull Requests — Team Merges
A Pull Request (PR) is a GitHub feature — not a Git command. Push your feature branch to GitHub, then open a PR to request that your branch be reviewed and merged into main. Teammates can comment, request changes, and approve before anything merges. The standard professional workflow.
Stash Commands
git stash                  # Save current uncommitted work to stash
git stash list             # See all stashed items
git stash pop              # Restore most recent stash AND delete it from stash
git stash apply            # Restore most recent stash AND keep it in stash list
git stash drop             # Delete most recent stash without applying
Rebase Workflow
# On your feature branch, rebase onto main
git checkout feature/login
git rebase main

# Result: your feature commits are replayed on top of the
# latest main — clean linear history instead of merge bubbles

BEFORE rebase:             AFTER rebase:
main:    A──B──C           main:    A──B──C
feature:    D──E                    └──D'──E' (replayed)

Pull Request Workflow on GitHub

1
Push Your Feature Branch
Complete your work on a feature branch and push it to GitHub: git push origin feature/login
2
Open a Pull Request on GitHub
GitHub will show a banner "Compare & pull request." Click it, write a description of your changes, and submit the PR. The PR page shows a full diff of every change you made.
3
Review, Approve & Merge
Teammates review your code, leave comments, request changes if needed. Once approved, click Merge pull request on GitHub. Your feature is now part of main. Delete the feature branch to keep things tidy.
🎯
The Daily Professional Workflow
In a real team: 1) git pull to get latest main. 2) git checkout -b feature/my-task to start a branch. 3) Code, then git add . && git commit -m "..." frequently. 4) git push origin feature/my-task. 5) Open a PR on GitHub for code review. 6) After approval, merge via PR and delete the branch. Repeat.
