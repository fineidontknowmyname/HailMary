  title="Setup & First Repository"
  desc="From zero to your first commit. Run these steps exactly once on a new machine."
>

<StepList>
  <Step num="1" title="Install Git">
    Download from [git-scm.com](https://git-scm.com) or via your package manager. Verify with <code>git --version</code>. You need `2.30+` for modern features.
  </Step>

  <Step num="2" title="Set Your Identity">
    Git stamps every commit with your name and email. Set them globally once:

    ```bash
    git config --global user.name "Ada Lovelace"
    git config --global user.email "ada@example.com"
    ```

    These live in `~/.gitconfig`. Use `--local` inside a repo to override per-project.
  </Step>

  <Step num="3" title="Set Your Default Branch to 'main'">
    The industry has moved away from `master`. Make `main` the default globally:

    ```bash
    git config --global init.defaultBranch main
    ```
  </Step>

  <Step num="4" title="Initialise a Repository">
    Navigate to your project folder and run:

    ```bash
    git init
    ```

    This creates the `.git` directory. Your project is now a Git repository. Nothing is committed yet.
  </Step>

  <Step num="5" title="Stage and Commit">
    ```bash
    git add .                          # Stage everything
    git commit -m "chore: initial commit"
    ```

    The `-m` flag takes your commit message inline. For longer messages, omit `-m` and Git opens your `$EDITOR`.
  </Step>

  <Step num="6" title="Connect to GitHub">
    Create a new repository on GitHub (no README, no `.gitignore`), then:

    ```bash
    git remote add origin https://github.com/you/repo.git
    git push -u origin main
    ```

    The `-u` flag sets `origin/main` as the upstream for this branch, so future pushes only need `git push`.
  </Step>

  <Step num="7" title="Authenticate with SSH (Recommended)">
    HTTPS asks for a password every time. SSH never does. Generate a key pair:

    ```bash
    ssh-keygen -t ed25519 -C "ada@example.com"
    cat ~/.ssh/id_ed25519.pub
    ```

    Copy the output and paste it into **GitHub → Settings → SSH Keys**. Done.
  </Step>
</StepList>

<Callout type="warn" title="Never Commit Secrets">
  If you push an API key, database password, or private key to GitHub — even for one second — rotate it immediately. Bots scan every public push in real time. Use a `.env` file and add it to `.gitignore` before your first commit.
</Callout>

</Section>

## The Commands You'll Use Every Single Day

The `git status` → `git add` → `git commit` loop is the heartbeat of Git. You'll type this sequence hundreds of times per week. Internalise it.

```
Working Tree  ──(git add)──▶  Staging Area  ──(git commit)──▶  Repository
     ▲                                                               │
     └────────────────────(git checkout)────────────────────────────┘
```

## Branching: The Workflow That Makes Teams Work

Branches let multiple developers work on isolated features simultaneously without tripping over each other.

```bash
git checkout -b feature/my-feature   # Create and switch to a new branch
# ... do work, commit ...
git checkout main                    # Switch back
git merge feature/my-feature         # Merge the work in
git branch -d feature/my-feature     # Clean up the branch pointer
```

**Try these commands in the sandbox:**

- `git status` — see the state of the working tree
- `git log --oneline` — view commit history (compact)
- `git branch` — list all local branches
- `git stash` — save uncommitted work without committing it
- `git add .` — stage all changes

<Callout type="tip" title="Use git log --oneline --graph --all">
  This one-liner gives you a visual ASCII graph of your entire branch history. Alias it: `git config --global alias.lg "log --oneline --graph --all --decorate"` — then just run `git lg`.
</Callout>

## Undoing Things: The Commands Devs Google Every Week

| Goal | Command |
|---|---|
| Unstage a file | `git restore --staged <file>` |
| Discard working tree changes | `git restore <file>` |
| Undo last commit, keep changes staged | `git reset --soft HEAD~1` |
| Undo last commit, keep changes unstaged | `git reset HEAD~1` |
| Nuke last commit entirely | `git reset --hard HEAD~1` |
| Revert a commit (safe, creates new commit) | `git revert <sha>` |

<Callout type="danger" title="reset --hard is permanent">
  `git reset --hard` rewrites history and discards changes with zero confirmation. There is no undo. If you've already pushed the commits you're resetting, you'll need a force push — which rewrites the remote's history and will wreck your teammates' branches.
</Callout>

<Section
  num="04"
  title="Best Practices & Pro Tips"
  desc="The habits that separate developers who fight Git from developers who command it."
>

<Callout type="tip" title="Write Conventional Commits">
  Use the Conventional Commits spec: `type(scope): description`. Types include `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `perf`. This makes your history machine-readable, enables automatic changelogs, and tells reviewers exactly what changed at a glance.

  ```
  ✅ feat(auth): add OAuth2 login with Google
  ✅ fix(api): handle null user_id in /progress endpoint
  ❌ git commit -m "stuff"
  ❌ git commit -m "fix"
  ```
</Callout>

<Callout type="warn" title="Commit Early, Commit Often">
  A commit is a save point. A branch costs nothing. Make small, atomic commits that do exactly one thing. If your commit message needs "and" in it, you should probably split it into two commits. `git add -p` lets you stage individual hunks within a file for surgical commits.
</Callout>

<Callout type="info" title="The Golden Rule of Rebasing">
  Never rebase a branch that others are working from. Rebasing rewrites commit SHAs — when a teammate pulls, Git sees entirely different commits and the history diverges. The rule: rebase your local feature branch onto `main` before opening a PR. Merge `main` into shared branches.
</Callout>

<Callout type="info" title="Use .gitignore Aggressively">
  Commit a `.gitignore` as the very first file in every repo. At minimum: `node_modules/`, `.env`, `.env.local`, `dist/`, `*.log`, `.DS_Store`. Use [gitignore.io](https://gitignore.io) to generate a complete file for your stack in seconds.
</Callout>

<Callout type="tip" title="Pull Requests Are Communication, Not Just Code">
  A great PR has: a one-line title (Conventional Commit format), a description of *why* (not what — the diff shows what), a testing checklist, and screenshots for UI changes. Reviewers are context-switched when they open your PR. Make their job effortless.
</Callout>

<Callout type="danger" title="Never Force-Push to a Shared Branch">
  `git push --force` on `main` rewrites the remote's history. Anyone who has already pulled will have a diverged history. If you absolutely must force-push (e.g. to fix a leaked secret), use `--force-with-lease` instead — it fails if anyone has pushed since you last fetched, preventing accidental overwrites.
</Callout>

<Callout type="tip" title="The Aliases That Will Save You Hours">

  ```bash
  git config --global alias.st   "status -sb"
  git config --global alias.lg   "log --oneline --graph --all --decorate"
  git config --global alias.undo "reset HEAD~1"
  git config --global alias.save "!git add -A && git commit -m 'chore: wip'"
  ```

  `git save` is your panic button — stage and commit everything when you need to switch context fast. Clean it up with `git undo` later.
</Callout>

</Section>
